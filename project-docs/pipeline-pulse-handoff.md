### Important: refreshing the calendar list alone will NOT populate Salesforce matches

Adam asked, correctly, how this tab is supposed to know *whose* Salesforce Lead/Contact/Account to find and update. Being precise about this, because it's easy to assume more automation is happening than actually is:

- **Knowing who's on the calendar is fully automatic and always current** — any session just calls `Google_Calendar` `list_events` fresh, no memory or prior knowledge required.

  1. Go to Salesforce and use the global search bar (top nav) with the attendee's **email address** — email is the one reliably unique identifier across Lead/Contact/Account, and searching by name risks false matches.

  4. If genuinely nothing comes back for that email in Salesforce at all, that's a real "not found" — it's fine and expected for e.g. a first-time inbound demo booking that hasn't been touched in Salesforce yet.
  5. ## Known issue: "Request refresh" button showing an error

If Adam reports the "Request refresh" button on the dashboard produced an error, this is almost always benign and NOT a sign the dashboard is broken:

- The button publishes a brand-new full version of the page, built on top of whatever version was loaded in his browser tab. If any chat (this one, another one, or the browser tab itself) has republished the artifact since his tab loaded, his tab's copy is stale, and the button's publish attempt is correctly rejected with a `conflict` error.
- Per the artifact platform's own design, `conflict` is routine, not a failure — the moment it happens, his browser tab is automatically reloaded to the current live version in the background. No data is lost. The button code (see the `catch` block in the page's script) already shows a reassuring message for this case ("A Claude session just updated this dashboard — reloading to show the latest version…") rather than a scary one — if you ever rewrite that script, preserve that distinction (branch on `err.code === 'conflict'` specifically; don't lump it in with real failures like `not_writer`).
- **Practical habit to reduce how often this happens:** if you're about to republish the dashboard from a check, and Adam might have the page open in a tab, mention that he should reload the tab before clicking anything on it afterward — a stale tab is the only real cause of this.
- Separately, there was a real bug (fixed 2026-08-25): `renderFullDocument()`'s style-capturing line used `document.querySelector('style')`, which — because the platform injects its own minimal reset `<style>` tag into `<head>` at serve time, ahead of the dashboard's own custom `<style id="pp-style">` block — grabbed the WRONG style tag and silently stripped all the dashboard's fonts/colors/layout on that publish. **If you ever touch `renderFullDocument()`, keep it targeting `document.getElementById('pp-style')`, never a bare tag-name selector**, or the same regression will recur.
- As of 2026-08-25 there is a pending, unactioned `refreshRequest` (Aug 25, 11:46 AM) sitting in the dashboard's state. Whoever runs the next Salesforce check should clear it (set `refreshRequest: null` after the check completes) rather than leaving it to linger.
